Yuying Jin / Experience / Frankenstein Variorum

Case study

From proofreader to co-author.

Frankenstein Variorum is a multi-year digital research project that compares five editions of Frankenstein, from 1816 to 1831, passage by passage. I joined to check the output of its data scripts. Over a year and a half I automated its data pipeline, rebuilt its reading viewer, contributed code to five of its repositories, and was credited as a co-author of the project.

Starting with the output

My first job was to run the data-processing scripts, proofread what came out, and log every error. Next came fixing the scripts themselves, so the same errors would stop appearing. My advisor, Elisa Beshero-Bondar, and I pair-programmed, with Elisa at the keyboard and me as the observer. As we went, I worked out what each part of the code did, asked questions, and proposed possible fixes alongside Elisa.

Automating the pipeline

Debugging alongside Elisa, I came to know what every code file did. That is when I took on automating the process, starting with learning shell scripting to handle the collation chunks. I spent nine hours learning and debugging, and that step ran on its own.

While it was fresh, I spent another eleven hours on the harder part: the post-collation pipeline, which runs more than a dozen scripts across more than a dozen folders over large batches of files. Both now run as single commands. Processing and checking hundreds of files, which had been impractical by hand, now takes about 2.5 hours, and new team members can verify their changes without learning the whole codebase.

That changed how the team worked. Elisa brought in two students to proofread, and with the scripts they could process the data and check the results themselves. I was free for harder problems, and their feedback told me where the processing code still went wrong. The deepest fix was in the encoding itself. Visually similar but different tokens in the TEI/XML were treated as equal, so a comparison could be wrong without anyone noticing. I fixed it in the encoding, where it started.

From the data to the website

Once the data problems were mostly solved, I proposed checking whether the processed data actually worked on the website. The project's web technology wasn't Elisa's area at the time, so she introduced me to Raff Viglianti, who had been on the project for years and had built its technical prototype.

The prototype was built with Gatsby, CETEIcean and React. I studied all three and found them hard; I didn't even know where to begin. Raff then suggested React and Astro and gave me a small starter Astro project. From there I learned React from zero, built the new viewer, and moved the old site's content onto the new stack. This was before tools like Cursor or Claude.

Polishing the viewer

Comparing five editions is hard on one screen; nobody can keep five windows open side by side. The prototype's answer was hotspots that show how much each passage varies across editions, and a side panel that shows the differing text. I built on those ideas and kept refining how they feel to use:

  • Moving between editions smoothly. I kept refining how readers switch between the pages of different editions until it felt seamless.
  • Landing on the right line. When a reader jumps from the side panel to see a variant in its own context, the page scrolls to that passage and highlights it, so they never have to hunt for it.
  • Chapters that don't line up. The same passage can sit under different chapter numbers in different editions. The edition and chapter selector handles that, so readers reach the same content wherever it was numbered.
  • Readable without color. Hotspots are gray, and the highlight colors that mark each edition are chosen so colorblind readers can tell them apart. For readers who see no color at all, a highlighted hotspot also gets a border above and below. Text that is missing from an edition is also marked differently from text that was changed, so a gap is never mistaken for a major revision.

Deciding where a fix belongs

The website also became the place where remaining data errors showed up. For each one I had to decide whether it belonged in the website's code or back in the data processing, and I talked those calls through with Elisa. One character-rendering bug looked like a quick fix with a regex in the viewer. Testing turned up too many edge cases, so I fixed it in the XSLT post-processing instead.

Where it ended up
